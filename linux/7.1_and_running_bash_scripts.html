Chapter 7: Automating Tasks with Bash Scripting#

1. Introduction#

This section introduces the fundamentals of automating tasks in a precision health environment using bash scripts. Imagine you’re at a facility like City Medical Center, where technicians run dozens of routine checks on data files every day. A simple script could automate a “file health check” on new lab reports, saving valuable time and preventing manual errors. In clinical and research settings, you often repeat the same sequence of commands daily, and scripts are the key to making this work efficient and reliable. The learning journey will cover how to create a simple script, make it executable, and run it using two different methods, laying the foundation for building powerful automation workflows.

2. Key Concepts and Definitions#

  • Bash Script: A plain text file containing a series of commands that are executed by the bash shell. In a medical context, a script could automate the process of downloading daily lab results, renaming them according to a patient ID convention, and archiving them.

  • Shebang (#!): The character sequence at the beginning of a script (#!/usr/bin/env bash) that tells the operating system which interpreter to use to execute the commands. This ensures that your script is consistently run by the bash shell, even if the user’s default shell is different, providing reliability for critical tasks like processing genomic data.

  • Execute Permission: A file system property that allows a file to be run as a program. Before a script can be run directly by its name (e.g., ./process_labs.sh), it must be granted execute permission. This is a security feature to prevent accidental execution of files, ensuring that only trusted scripts, such as those for patient data anonymization, are run.

  • Execution Path (./): A prefix used to specify the location of a script in the current directory. When you type ./script.sh, you are explicitly telling the shell to run the script.sh file located right here. This prevents the system from accidentally running a different program with the same name that might exist elsewhere in the system’s path, which is crucial for maintaining data integrity in a clinical environment.

3. Main Content#

3.1. Create and Run a Reusable Script#

This is the standard method for scripts you intend to use regularly. By making the script executable, you treat it like any other command-line program.

1. Create the Script File

Use a text editor like nano to create a file. While the .sh extension is not technically required for the script to run, it is a universal convention that helps developers quickly identify the file as a shell script.

vim process_labs.sh

Try it yourself: Modify the code above or write your own version

Add the following content. The shebang is critical, and using a variable for the PATIENT_ID makes the script easier to update.

#!/usr/bin/env bash
# This script prints a mock lab result status.
# Define a variable for the patient ID for easy updates.
PATIENT_ID="PT098765"
echo "Initializing lab result processing..."
echo "Processing file: CHEM7_20251110.csv"
echo "Patient ID: $PATIENT_ID"
echo "Processing Status: Complete"

2. Grant Execute Permission

Use the chmod (change mode) command to add the execute (+x) permission to your script.

chmod +x process_labs.sh

Important: Using chmod +x is convenient but grants execute permission to everyone on a multi-user system. For scripts containing sensitive operations or data paths, it is a critical security best practice to use chmod u+x, which restricts execution permission to only your user account (the user who owns the file).

3. Run the Script

Execute the script by providing its path from the current directory.

./process_labs.sh

Debug Note: If you try to run process_labs.sh without the ./ prefix, you will likely get a “command not found” error. This is because the current directory is not typically in the system’s $PATH for security reasons. The ./ explicitly tells the shell to look right here.

The expected output will be:

Initializing lab result processing...
Processing file: CHEM7_20251110.csv
Patient ID: PT098765
Processing Status: Complete

Exercise 1: Create and Run a Basic Script#

Create a script named init_analysis.sh. Make it executable and have it print the following two lines to the terminal: Initializing sequence analysis... Ready for data input.

Confirm it runs correctly using both ./init_analysis.sh and bash init_analysis.sh.

Solution

1. Create the file: nano init_analysis.sh 2. Add content:

#!/usr/bin/env bash
echo "Initializing sequence analysis..."
echo "Ready for data input."

3. Grant permission: chmod +x init_analysis.sh 4. Run with path: ./init_analysis.sh 5. Run with interpreter: bash init_analysis.sh

Reflection Moment: Why does the bash init_analysis.sh command work without execute permission?

Think about it this way: When you use ./init_analysis.sh, you are asking the operating system to run the file. The OS checks for execute permission as a safeguard. However, when you run bash init_analysis.sh, you are not asking the OS to run the file directly. Instead, you are running the bash program (which already has execute permission) and simply giving it the init_analysis.sh file as an input to read and process. The bash interpreter reads the commands line-by-line, so the script file itself doesn’t need to be executable.

Key Learning: A script can be executed directly if it has +x permission or passed as an argument to an interpreter like bash regardless of its permissions.

Exercise 2: Create a Patient Data Directory#

Objective: Write a script that performs a file system operation. Time: 5 minutes Medical Context: You need to quickly create a standardized directory structure for a new patient’s electronic health records (EHR).

Create a script named new_patient.sh. The script should print “Creating directory for new patient…” and then create a new directory named patient_data_001. Run the script and verify the directory was created using the ls command.

Solution

1. Create the file: nano new_patient.sh 2. Add content:

#!/usr/bin/env bash
# This script creates a directory for a new patient.

echo "Creating directory for new patient..."
mkdir patient_data_001
echo "Directory 'patient_data_001' created."

3. Grant permission: chmod +x new_patient.sh 4. Run the script: ./new_patient.sh 5. Verify: ls (You should see patient_data_001 in the output).

Explanation: This script combines an informational echo command with a functional mkdir command. This is a common pattern for providing feedback to the user while the script runs.

Key Learning: Scripts can execute any command you would normally type into the terminal, including commands that create files and directories.

Exercise 3: Explain Execution Methods#

Objective: Articulate the difference between the two execution methods. Time: 5 minutes Medical Context: A colleague has two scripts: run_daily_report.sh (run every morning) and fix_corrupt_file.sh (a one-time fix). They are unsure which execution method to use for each.

Create a script named explain_methods.sh that uses echo commands to print an explanation of when to use ./script.sh versus bash script.sh. The explanation should reference your colleague’s two scripts.

Solution

1. Create the file: nano explain_methods.sh 2. Add content:

#!/usr/bin/env bash
# This script explains the two execution methods.

echo "Choosing the right execution method:"
echo "------------------------------------"
echo "For 'run_daily_report.sh', use 'chmod +x' once, then run with './run_daily_report.sh'."
echo "This is best for reusable, trusted scripts that act like regular commands."
echo ""
echo "For 'fix_corrupt_file.sh', you can simply use 'bash fix_corrupt_file.sh'."
echo "This is ideal for one-off scripts where you don't need to permanently change permissions."

3. Grant permission and run: chmod +x explain_methods.sh && ./explain_methods.sh

Explanation: This exercise reinforces the conceptual difference between the two methods. The ./script.sh method is for established, routine tools, while the bash script.sh method is for temporary or single-use tasks.

Key Learning: The choice of execution method depends on the script’s intended use case: frequent and routine vs. temporary and single-use.

5. Practical Applications#

  • Automated Daily Lab Report Generation: In a clinical lab, a script can be written to query a database for the day’s results, format them into a report, and email it to the supervising physicians. This script would be made executable (chmod +x) and scheduled to run automatically every morning, ensuring timely and consistent reporting.

  • Batch Renaming of Imaging Files: A researcher receives a dataset of 1,000 MRI scans with non-standard names. A bash script can be written to loop through all files and rename them according to a consistent PatientID_ScanDate_View.nii format. This would be run once using the bash rename_scans.sh method, as it’s a one-time data preparation task.

  • Initializing a New Analysis Environment: When a new genomic dataset arrives, a bioinformatician can run an executable script (./setup_project.sh) that creates a standard directory structure (/data, /scripts, /results, /logs), copies template configuration files, and prints instructions for the next steps. This ensures every project starts with a consistent and organized foundation.

6. Summary and Key Takeaways#

In this section, we’ve explored how to create, add permissions to, and execute bash scripts—a core skill for automation in any data-driven field, including precision health. By bundling commands into a script, you create a reusable, reliable, and efficient tool for repetitive tasks.

  • Scripts are text files: A bash script is simply a text file with a list of shell commands.

  • The Shebang is essential: The #!/usr/bin/env bash line ensures your script is run by the correct interpreter.

  • Permissions are key: A script must have execute permission (chmod +x) to be run directly as a command (./script.sh).

  • Two ways to run: You can execute a script directly if it has the right permissions (./script.sh) or pass it to the interpreter manually (bash script.sh), which bypasses the permission requirement.

Mastering these fundamentals prepares you for the next step: making your scripts more dynamic and powerful by using variables.
